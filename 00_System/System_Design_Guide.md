# System Design Guide

- 状态：Active
- 版本：v0.2.2
- 所属模块：System Design Guide
- 更新频率：仅在系统设计原则发生明确变化时更新

## Purpose

System Design Guide 用于回答“Yu-AI-OS 应该如何设计、扩展和维护？”，为系统文档与模块提供长期一致的设计规范。

缺少统一设计规范时，系统容易出现职责重复、内容混杂、权威来源不清和短期信息进入长期结构的问题。

## 一句话核心

任何新文档或新模块，在开始编写内容之前，必须先明确其存在意义、职责、边界和章节结构。

## 负责的内容

- 定义 Yu-AI-OS 长期采用的系统设计原则。
- 规定文档与模块的职责划分方法。
- 提供新文档设计前必须完成的检查。
- 定义系统文档的状态生命周期和版本规则。
- 为长期扩展和维护提供一致的审核依据。

## 不负责的内容

- 不定义用户价值观、身份或人生目标。
- 不定义当前项目、学习计划、Daily 内容或 Strategic Goals 内容。
- 不定义具体模块的业务内容。
- 不记录 AI 工具分工或具体工作流细节。
- 不提供 Git 操作教程。
- 不代替 Human（用户）做方向、价值观或人生目标决定。

## Core Principles

### 设计先于实现

任何新文档或新模块，在开始编写内容之前，必须先明确其存在意义、职责、边界和章节结构。

固定顺序：

1. 明确存在意义。
2. 明确职责与边界。
3. 设计一句话核心和章节结构。
4. Human（用户）确认方向。
5. 实现。
6. Review（审核）。

不要在职责尚未确认时直接生成大量正文。

具体协作与 Git 流程以 `Workflow.md` 为权威文档。

### 单一核心职责与清晰边界

每份文档必须有一个可独立说明的核心职责。文档可以包含多个紧密相关的子内容，但不能成为无边界的杂项集合。

不同文档不得共同维护同一类核心职责。文档之间可以引用和依赖，但权威维护位置必须明确。

如果删除一份文档后，无法说明系统会失去什么，应重新判断其职责或存在必要性。

### 单一事实来源

同一事实只应有一个权威维护位置，即单一事实来源（Single Source of Truth）。

- 职责边界回答：哪份文档负责哪类问题。
- 单一事实来源回答：某一具体事实由哪里权威维护。
- 其他文档需要使用该事实时，应引用或简要概括，不应完整复制。
- 时间、状态、版本、目标和规则不得在多个文档中分别维护。
- 发现重复时，应先确定权威文档，再删除或缩减其他位置的重复内容。

当前系统的基本归属示例：

- 最高治理与权限边界：`AI_Constitution.md`
- 长期身份和价值观：`Identity.md`
- 长期方向：`Vision.md`
- 阶段目标与期限：`Strategic_Goals.md`
- 协作与执行方法：`Workflow.md`
- 系统设计规则：`System_Design_Guide.md`
- 重要系统决定、理由、证据与替代历史：`Decision_Log.md`
- 自动审核规则：`Review/Policy.md`

`Decision_Log.md` 保存重要决定的证据与历史；当前规范仍由对应职责的权威文档维护，Decision Log 不自动修改其他权威文档。`Review/Policy.md` 只负责自动审核规则，不拥有 Human Decision 权限。

### 内容迁移完整性

重构文件时，不得静默删除仍然有效的内容。

不属于当前文件的内容，必须明确判断为：

- 永久删除
- 已在其他权威文件中存在
- 建议迁移
- 暂缓处理

其中：

- 永久删除必须有明确理由，例如内容错误、已经过期或不再具有长期保存价值。
- 已在其他权威文件中存在时，必须能够指出对应的权威事实来源。
- 目标文件或模块尚未设计时，应暂缓处理，不得为了迁移单条内容擅自创建未经设计的新模块。
- 具体的审计、Human 确认、跨文件修改、Review 和 Commit 流程，以 `Workflow.md` 为准。

### 最小必要设计

先搭框架，使用时再增加经过验证的内容。

- 先建立能够使用的最小框架。
- 没有真实需求或明确依据时，不提前创建和填满模块。
- 新规则应解决已经出现或可以明确预见的问题，并允许系统随真实使用逐步扩展。

### 长期内容与阶段内容分离

只有同时满足以下条件的内容，才适合进入 `00_System`：

- 长期相对稳定
- 跨阶段使用
- 跨模块产生影响
- 属于整个 Yu-AI-OS 的系统级规则或基础定义

长期内容不一定都属于系统层。个人长期学习方向、职业规划或关系目标，仍可能属于其他长期模块。

阶段性目标、当前任务、学习内容、项目状态和执行记录，不进入系统层。

### Human 决定方向

Human（用户）对以下内容拥有最终决定权：

- 决定价值观
- 决定人生方向
- 确认重要职责边界
- 对最终内容负责

AI 可以辅助澄清、分析、组织、实现和审核，但不能替代 Human（用户）创造价值观或决定人生方向。具体协作分工以 `Workflow.md` 为权威文档。

## 与 Workflow.md 的关系

- `System_Design_Guide.md` 定义系统设计和文档边界原则。
- `Workflow.md` 定义这些原则如何进入实际协作、审核、迁移和 Git 流程。

## 文档设计检查清单

以后设计任何文档，都应先回答：

1. 为什么需要这份文档？
2. 如果删除它，系统会失去什么？
3. 它负责什么，又不负责什么？
4. 一句话核心是什么？
5. 权威信息来源在哪里，是否与其他文档重复？
6. 它属于长期系统层，还是阶段性或专业模块？
7. 当前是否确实需要它，哪些内容必须由 Human（用户）决定？

如果核心职责、边界或权威来源无法明确，应暂停实现并继续完成设计。

对于系统层文档，可以额外判断其内容在多年后是否仍具有稳定意义，但这不是所有文档的强制标准。

## 职责冲突处理

当两个或多个文档可能负责同一内容时，按以下顺序处理：

1. 判断内容属于身份、方向、阶段目标、执行方法或其他类型。
2. 确定唯一的权威维护位置。
3. 其他文档删除重复内容，或只保留必要引用。
4. 涉及价值观、人生方向或重要职责调整时，由 Human（用户）最终决定，并在相关版本记录中说明。

System Design Guide 提供裁决规则，但不自动成为所有内容的权威来源。

## 文档生命周期

系统文档统一使用以下状态：

- Draft：正在设计或编写，尚未完成审核
- Active：当前有效并正式使用
- Deprecated：仍保留，但已不建议继续使用
- Archived：停止维护，仅作为历史记录保存

- 只有替代方案稳定后，旧文档才进入 Deprecated。
- Archived 文档原则上不再修改。
- 仍具有历史价值的系统文档不应直接删除。
- 当前状态只在顶部元数据中维护。

## 版本规则

文档版本采用 `Major.Minor.Patch` 格式，例如 `1.2.3`。

| 类型 | 适用情况 | 示例 |
| --- | --- | --- |
| Patch | 拼写、格式、引用及不改变原意的表达修正 | `0.0.1 → 0.0.2` |
| Minor | 新增原则、章节或规则，但不改变核心定位 | `0.0.2 → 0.1.0` |
| Major | 核心职责、边界或兼容性发生重大变化 | `0.3.0 → 1.0.0` |

- Draft 阶段可以使用 `0.x.x`。
- 不因每次保存或 Commit 自动升级版本。
- 只有内容发生实际版本变化时才升级。
- 最终版本由 Human Review（人工审核）后确认。

## 更新规则

- 仅在 Yu-AI-OS 的长期设计原则发生明确变化时修改本文。
- 不因短期目标、当前项目、学习计划或 Daily 内容变化而修改。
- 更新前应确认变化影响的文档范围和职责边界。
- 重要修改需要 Human（用户）最终审核。
- 每次更新应保留版本记录，并如实标明文档状态。
