# 工作流程

- Status: Active
- Version: v0.5.0
- Update Frequency: 当核心协作职责、任务流程、读取规则、审核方式或 Git 授权边界发生明显变化时更新

`v0.5.0 Active` 已于 2026-08-05 根据明确 Human Decision 建立普通修改直推 `main`、高风险修改使用 Draft PR 的长期 Git 工作模式，并成为当前 Workflow 基线。

## 文档目的

本文档定义 Yu-AI-OS 中的工作如何被提出、理解、分析、设计、执行、审核、验证、批准、提交，并在必要时发布。

它通过明确职责和授权，减少未经确认的修改、有效信息丢失与执行范围失控，在任务质量、风险控制和执行效率之间保持平衡。

## 一句话核心

根据任务风险，在正确时点读取必要的权威信息；由 Human（用户）确认范围和重要决策，由 AI 执行、审核和验证，并仅在获得相应授权后进行 Git 写入或发布操作。

## 本文档负责什么

- Human、ChatGPT 和执行型 AI 的角色与职责
- 简单任务与复杂任务的分类方式
- 任务从提出到完成的标准流程
- 系统文档的任务相关读取规则
- 系统文档在任务生命周期中的读取时机
- 任务范围或风险变化时的重新读取规则
- Review（审核）与集中修改方式
- 文档重构与内容迁移闭环
- Git 操作与 Human 授权边界
- AI 能力选择原则
- Handoff 与任务状态文件的更新条件

## 本文档不负责什么

本文档不定义：

- Human 的身份、价值观和长期行为倾向
- 长期人生愿景和理想状态
- 当前阶段战略目标、优先级和成功标准
- 系统架构和文档设计原则
- 当前任务进度和未完成事项
- Daily 计划和具体日程
- 具体学习方法
- 具体项目实现方案
- 某次任务的临时决策
- 某个具体 AI 产品的使用说明

## 角色与职责

### Human

Human（用户）负责：

- 提出功能需求。
- 决定产品方向。
- 提出真实需求。
- 提供必要且准确的事实。
- 说明限制条件、偏好和禁止事项。
- 确认任务目标、修改范围和完成标准。
- 审核复杂或高风险方案。
- 决定重要内容是删除、保留、迁移还是暂缓。
- 决定是否允许 `git add`。
- 决定是否允许 Commit。
- 决定是否允许 Push。
- 决定是否创建 PR，以及 PR 的仓库、目标分支和 Draft/Ready 状态。
- 单独明确决定是否 Merge。
- 作出重要授权和最终 Merge 决定。
- 在理解重要结果及其影响后再批准。
- 对最终方向、重要内容和发布结果拥有最终决定权。

Human 不承担日常代码审核或技术报告分析，也不应被当作报告搬运工。重要职责、不可逆操作和外部发布结果必须保留 Human 的最终决定权。

### ChatGPT

ChatGPT 负责：

- 担任 Yu-AI-OS 开发的 Tech Lead。
- 分析 Human 的真实需求。
- 理解并拆解需求，制定里程碑范围和完成标准。
- 明确目标、范围和完成标准。
- 识别风险、冲突和信息缺口。
- 判断需要读取哪些权威文件。
- 判断任务属于简单任务还是复杂任务。
- 设计解决方案和 Review 标准。
- 审核执行型 AI 的结果。
- 检查职责边界和信息完整性。
- 为执行型 AI 生成清晰、可执行、范围明确的指令。
- 审核 Codex 的最终报告，判断完成、返工或进入下一里程碑。
- 使用简短、易懂的中文向 Human 汇报里程碑进度。
- 在信息不足时明确说明不确定性。
- 不根据缺失信息自行编造事实。
- 不代替 Human 创造价值观、人生目标或最终战略决定。
- 不把未经 Human 确认的建议描述为已确认决定。

### 执行型 AI

当前主要由 Codex 承担执行型 AI 的职责，也可以根据任务需要由其他满足要求的实现工具承担。长期规则以能力和职责为准，而不是以具体产品为准。

执行型 AI 负责：

- 由 Codex 担任执行型开发者，并在授权范围内连续完成整个里程碑。
- 编写里程碑所需的代码和文档。
- 读取 Human 指定的文件。
- 读取任务必需的仓库实际状态。
- 根据已确认的指令执行修改。
- 不擅自扩大修改范围。
- 不擅自修改未授权文件。
- 运行任务需要的检查和验证。
- 完成测试和自检后集中报告。
- 如实报告修改内容、检查结果、错误、风险和限制。
- 如实报告 Git 状态。
- 不伪造完成状态。
- 不伪造测试、检查或验证结果。
- 发现范围扩大、事实冲突或授权不足时暂停并报告。
- 只在获得对应授权后执行 Git 写操作。
- 不因拥有执行能力而自行决定产品方向或重要内容。

## 任务分类与风险比例原则

流程复杂度应与任务风险成比例。简单任务不承担不必要的流程成本，高风险任务不得为了速度跳过必要的读取、确认、审核和验证。

### 简单、明确、低风险任务

典型情况包括：

- 单文件格式调整
- 错字修正
- 已确认内容的准确翻译
- 明确且局部的措辞修正
- 已通过 Human 审核文件的指定本地提交
- 不改变职责和事实来源的小型修改

可以使用简化流程：

1. 确认范围。
2. 读取目标。
3. 执行。
4. 检查。
5. 报告。

简单任务通常可以省略独立的大型设计方案、不相关核心文件的全量读取和不必要的多轮确认，但仍必须遵守授权范围、检查实际修改并如实报告结果。

### 复杂、跨文件或高风险任务

典型情况包括：

- 核心文档重构
- 架构调整
- 删除长期内容
- 内容跨文件迁移
- 合并或拆分文件
- 调整权威事实来源
- 多个核心文件之间的职责调整
- 修改 Git 历史
- Push、创建 PR、Merge 或发布
- 可能导致数据丢失的操作

此类任务必须使用完整流程，并在重要决策前获得 Human 确认。

完整流程是风险控制框架，不是机械形式主义。

## 里程碑开发模式

Yu-AI-OS 默认按完整里程碑推进，而不是按单个文件或小功能推进。里程碑由 ChatGPT 作为 Tech Lead 明确范围和完成标准，由 Codex 在已授权范围内连续实施、验证并形成最终报告，Human 负责产品方向、重要授权和最终 Merge 决定。

典型汇报节点包括：

- 第一层核心治理完成；
- Skill Framework 完成；
- Feynman 学习系统完成；
- Memory System 完成。

完成一个文件、一个小功能、一次普通测试、可自行解决的实现细节或不影响范围与目标的小型调整，不构成中途汇报或暂停理由。

### 中途暂停条件

只有出现以下情况时，才提前暂停：

- 里程碑全部完成；
- 出现无法在当前授权范围内自行解决的真实阻塞；
- 需要明显扩大已授权范围；
- 权威文件出现无法可靠判断的冲突；
- 可能造成数据丢失；
- 需要 Human 提供新的关键事实；
- 需要新的 Git、发布或 Merge 授权。

普通技术判断由 ChatGPT 和 Codex 在已授权范围内完成，不要求 Human 承担日常技术审核。

### 里程碑汇报

里程碑完成时只进行一次集中汇报。对 Human 的默认汇报应使用简短、易懂的中文说明：

- 做完了什么；
- 有没有问题；
- 当前处于什么状态；
- 下一里程碑是什么。

详细技术信息可以保留在 Codex 报告、Pull Request 或仓库中，但不要求 Human 阅读冗长技术内容。

### 新窗口恢复

新的 ChatGPT 窗口开始或恢复 Yu-AI-OS 开发时，应优先读取：

- `00_System/Workflow.md`；
- `00_System/Handoff/Latest.md`；
- 当前 Git 状态；
- 当前未提交修改或相关 Pull Request。

完成核验后恢复 Tech Lead 里程碑开发模式，不依赖旧聊天窗口的完整上下文。Handoff 仍是 dated snapshot；如与当前 Git 状态或权威文件冲突，以实际 Git 状态和对应权威文件为准。

里程碑开发模式不扩大任何 Git 或发布授权。`git add`、Commit、Push、PR 和 Merge 仍遵守本文的工作模式与授权边界，Merge 始终需要 Human 单独明确决定。

## 标准工作模式

工作模式用于让流程成本与实际风险和授权范围相匹配。普通修改默认使用 Direct Push 模式；命中高风险条件时使用高风险 PR 模式。工具能力本身不得成为扩大授权的理由。

### 1. 本地工作模式

本地工作模式用于尚未要求同步到 GitHub 的工作，允许：

- 读取任务所需文件和 Git 状态；
- 修改 Human 已授权范围内的本地文件；
- 运行必要检查和测试；
- 仅在 Human 明确发送 Handoff 触发口令时更新本地 Handoff。

默认不允许：

- `git add`；
- Commit；
- Push；
- 创建或修改 PR；
- Merge；
- 发布或其他外部写入。

普通开发和本地维护不应为每个小步骤重复请求 PR 或 Merge，也不应因为任务完成而自动更新 Handoff。

### 2. Direct Push 模式

Human 已对 `yuhaojie6275-bot/Yu-AI-OS` 建立有边界的长期授权：普通修改完成 Review 和必要检查后，Codex 可以将本次相关文件 `git add`、使用有意义的规范 Commit Message 提交，并 Push 到默认分支 `main`，无需逐次申请 Git 授权，也不创建 Pull Request。

该授权只适用于当前仓库中的普通修改，并持续有效，直到 Human 明确说“停止直推”或“恢复 PR 模式”。每次 Direct Push 前必须：

- 核实当前分支、Git 状态、实际 diff 和本次文件范围；
- 确认没有未预期或无关修改；
- 完成与风险相称的检查；
- 使用能说明类型、模块和目的的 Commit Message；
- Push 成功后报告修改文件、修改原因、测试结果和 Push 状态。

Commit Message 应明确表达类型、模块和目的，例如 `feat(daily): redesign Daily Brief`、`fix(calendar): resolve timezone parsing`、`docs(system): update architecture` 或 `refactor(memory): simplify cache layer`。不得使用 `Update`、`Fix bug`、`Misc`、`Temp` 等无法说明内容的标题。Direct Push 授权不包含强制 Push、Amend、Rebase、Reset、历史重写、Merge、删除分支、仓库设置修改或其他超出当前任务的操作。

### 3. 高风险 PR 模式

出现以下任一情况时，不得 Direct Push，必须创建开发分支，完成 Commit 和 Push，并自动创建以 `main` 为目标分支的 Draft PR：

1. 修改数据库 Schema、Prisma、Migration、SQL 或同类数据库结构文件；
2. 一次删除超过 10 个文件；
3. 修改 GitHub Actions、CI/CD 或 Workflow；
4. 修改 `package.json`、`package-lock.json`、`pnpm-lock.yaml` 或进行依赖升级；
5. 修改系统 Prompt、`AI_Constitution.md`、Core Rules 或 Security Rules；
6. 一次修改超过 30 个文件；
7. Human 明确说“创建PR”“创建 PR”“Review”或“Code Review”。

高风险 PR 模式已获得创建分支、暂存本次相关文件、Commit、Push 和创建 Draft PR 的长期授权，但不包含 Merge。Human 必须单独明确决定是否 Merge。无法可靠判断是否命中高风险条件时，按高风险处理。

### 4. 治理变更模式

治理变更模式适用于：

- AI Constitution；
- Human Authority；
- 权限或安全边界；
- Workflow 核心授权规则；
- 重大 Decision；
- 文档 Activation；
- 系统架构和职责边界；
- Review Bridge 安全机制；
- 高风险或难以撤销的变更。

此模式要求：

- 完整读取相关权威文件；
- 明确候选版本和影响范围；
- 必要时建立 Proposed Decision；
- 完成 Human Review；
- 获得明确 Human Acceptance；
- 将 Activation 与 Merge 分开授权；
- 将自动审查仅作为 advisory，不得用其替代 Human Decision。

### 模式选择原则

- 只做本地修改时使用本地工作模式；需要同步的普通修改默认使用 Direct Push 模式。
- 命中任一高风险条件时使用高风险 PR 模式，不得为了省略 PR 而缩小或错误描述范围。
- 不得因为工具具备远端能力而自动升级模式。
- AI 不应把一个明确、低风险、本地任务拆成多个无价值授权步骤。
- 风险或范围增加时必须暂停并重新判断模式。
- Human 可以随时缩小、终止或撤销当前模式授权。
- 不确定时保持较低权限模式。
- 效率优化不能绕过 Human Authority、真实性、验证或安全边界。

### Handoff 触发规则

Handoff 不在每个任务后自动更新。只有 Human 明确发送以下口令或等价的明确表达时才触发：

- `更新 Handoff`
- `更新handoff`
- `更新交接`
- `今天收尾`

触发后只更新本地 Handoff，不自动 Commit、Push、创建 PR 或 Merge。普通讨论、只读检查和小修改不触发 Handoff。Handoff 应总结阶段结果，不记录无意义流水账。

## 系统文档读取规则

系统文档采用任务相关读取，不采用固定的全量读取顺序。

1. 先读取 Human 当前指令明确指定的文件。
2. 读取当前任务直接修改的目标文件。
3. 读取完成任务必需的仓库状态。
4. 判断任务涉及哪一种权威事实。
5. 只读取与该事实直接相关的核心文件。
6. 发现职责冲突、信息不足或跨模块影响时，再扩大读取范围。
7. 不得因为文件位于 `00_System` 就无条件读取全部文件。
8. 不得以节省上下文为理由忽略完成任务必需的权威文件。
9. 不得只依赖聊天记忆代替当前仓库中的实际文件。
10. 发生事实冲突时，以对应职责的权威文件为准，并向 Human 报告冲突。
11. 无法判断权威来源时，应暂停重要修改并请求 Human 确认。

| 任务涉及的内容 | 权威文件 |
| --- | --- |
| 最高治理边界、Human Authority、授权、例外和不可违反原则 | `AI_Constitution.md` |
| 稳定身份、价值观、长期行为倾向 | `Identity.md` |
| 长期方向和理想状态 | `Vision.md` |
| 当前阶段成果、优先级、成功标准和战略风险 | `Strategic_Goals.md` |
| 系统结构、文档边界和设计规则 | `System_Design_Guide.md` |
| 协作、审核、执行、读取规则和 Git 授权 | `Workflow.md` |
| 重要系统决定、决定理由、证据和替代关系 | `Decision_Log.md` |
| 自动审核范围、安全规则、模型配置和输出契约 | `Review/Policy.md` |
| 当前状态、未完成事项和任务上下文 | Handoff 或任务文件 |
| 具体学习、项目和 Daily 内容 | 对应专业模块 |

读取与实施必须遵守以下规则：

- 涉及行为是否允许、权限边界或治理冲突时，读取 `AI_Constitution.md`。
- 涉及既有重要 Human Decision 及其理由时，读取 `Decision_Log.md`。
- 涉及自动审核行为时，读取 `Review/Policy.md`。
- Decision Log 中的决定不自动授权实施；实施仍需要当前操作所要求的 Human Authorization。
- Handoff 仍然只是当前状态快照，不是长期决策或授权来源。
- 自动审核结果不能代替 Human Review 或 Merge Approval。

## 系统文件的读取时机

系统文件不是只在任务开始时读取一次，也不是按照固定顺序全部读取。应根据任务生命周期中的触发时点按需读取。

### 新任务开始时

优先读取：

- Human 当前指令
- 当前任务直接涉及的文件
- 本次允许修改的目标文件
- 必要的仓库状态
- 与任务直接相关的任务说明文件

开始分析前，应判断任务是否涉及身份和价值观、长期方向、战略优先级、系统设计、Workflow 与 Git 授权或当前任务状态，再决定是否读取对应权威文件。

此时不应无条件读取全部系统文件。

### 恢复中断任务时

优先读取：

- Handoff
- 当前任务文件
- 当前 Git 状态
- 未提交 diff
- 最近相关 Commit
- 上一次明确记录的未完成事项

不得仅依赖 AI 的聊天记忆、模糊总结或对上一次进度的猜测。

如果 Handoff 与当前仓库状态不一致，应以实际仓库状态为事实基础，并报告不一致。

### 分析和设计方案前

应先判断任务涉及哪类权威事实，并读取对应文件：

- 涉及身份、价值观或长期行为倾向时，读取 `Identity.md`。
- 涉及长期方向时，读取 `Vision.md`。
- 涉及阶段目标、优先级或成功标准时，读取 `Strategic_Goals.md`。
- 涉及系统结构、文件职责或设计边界时，读取 `System_Design_Guide.md`。
- 涉及协作、审核、迁移或 Git 授权时，读取 `Workflow.md`。
- 涉及当前进度和未完成事项时，读取 Handoff 或任务文件。

复杂或高风险任务必须在 Human 确认方案前完成必要的权威文件读取。简单任务不要求为了形式完整而读取全部核心文档。

### 执行修改前

执行型 AI 必须核实：

- Human 已确认的执行指令
- 本次允许修改的文件
- 当前目标文件内容
- 与修改直接相关的权威文件
- 当前 Git 状态
- 当前工作区是否存在未预期修改

不得仅根据 ChatGPT 的摘要替代必须核实的实际文件内容。如果执行指令已完整包含必要规则，也不得因此重复读取与任务无关的全部仓库。

### 任务范围或风险发生变化时

出现以下情况时，必须暂停执行并重新判断读取范围：

- 需要修改未授权文件
- 任务从单文件扩大为跨文件任务
- 不同权威文件之间存在冲突
- 内容需要删除或迁移
- 文件需要合并或拆分
- 文件职责需要调整
- 原有完成标准无法满足
- 当前方案可能导致信息丢失
- 需要进行未授权的 Git 操作
- 当前信息不足以安全继续

此时应：

1. 停止扩大修改。
2. 读取新受影响模块的权威文件。
3. 分析新增影响。
4. 向 Human 报告范围变化。
5. 获得确认后再继续。

不得先修改后补授权。

### Review 时

Review 不只检查修改后的文字或代码，还应重新核对：

- Human 确认的目标
- 修改范围
- 完成标准
- 禁止事项
- 本次使用的权威文件
- 修改前后的差异
- 事实是否准确
- 职责是否冲突
- 是否遗漏有效信息
- 是否出现未经授权的范围扩大
- 验证结果是否真实

文档重构或内容迁移任务还必须同时检查来源文件、目标文件、内容遗漏、内容重复和权威事实来源。

### Commit 前

通常不需要重新读取全部系统文件，但必须检查：

- 最终 diff
- `git status`
- 暂存范围
- 修改文件列表
- 必要检查和验证结果
- Commit message
- Human 是否已授权 Commit

核心文档、跨文件修改、权威事实来源调整、内容迁移或其他高风险任务，还应确认最终结果符合 Human 已批准方案、相关权威文件和文件职责边界。

不得为了形式完整而在 Commit 前机械读取所有系统文件。

### 任务完成后

只有 Human 明确触发 Handoff，且以下内容实际发生变化时，才更新 Handoff。其他任务状态文件仅在其负责的状态实际变化且位于授权范围内时更新：

- 当前状态
- 未完成事项
- 下一步
- 当前分支
- 重要决策
- 后续恢复任务所需的上下文

不得为了形式完整，在每次任务结束后修改所有系统文件。长期核心文件只在其负责的长期事实或规则真正变化时更新。

| 任务阶段 | 必须优先读取或核实 |
| --- | --- |
| 新任务开始 | Human 当前指令、目标文件、必要仓库状态 |
| 恢复中断任务 | Handoff、任务文件、Git 状态、未提交修改 |
| 分析与设计前 | 与任务事实类型对应的权威文件 |
| 执行修改前 | 已确认指令、允许修改的文件、直接相关权威文件、Git 状态 |
| 范围或风险变化时 | 新受影响模块对应的权威文件 |
| Review 时 | 完成标准、修改结果、相关权威文件和实际 diff |
| Commit 前 | 最终 diff、Git 状态、验证结果、暂存范围和授权 |
| 任务结束后 | 仅在状态实际变化时更新 Handoff 或任务文件 |

## 标准工作流程

1. Human 提出需求并提供必要事实。
2. 明确任务目标、修改范围、完成标准和禁止事项。
3. 读取当前任务、目标文件和必要仓库状态。
4. 判断需要读取哪些权威文件，并在正确时点读取。
5. 分析职责边界、风险、冲突和信息缺口。
6. 对复杂或高风险任务，由 Human 确认方案。
7. 执行型 AI 按确认范围实现。
8. 形成完整 Draft 或完整修改结果。
9. 对事实、结构、职责、边界和信息完整性进行完整 Review。
10. 集中处理本轮 Review 发现的问题。
11. 执行最终检查和验证。
12. 高风险、治理或其他重要结果由 Human 在最终生效前审核；普通修改在 standing authorization 内完成自检和验证。
13. 按 Direct Push 或高风险 PR 模式执行 `git add`、Commit 和 Push。
14. 只有命中高风险条件时创建 Draft PR；普通修改禁止创建 PR。
15. Merge 必须获得 Human 单独明确决定。
16. Human 明确触发且当前状态实际变化时，更新 Handoff；其他任务文件仅在状态实际变化且获得相应授权时更新。

简单任务可以省略不必要的独立设计阶段。完整流程可以按风险缩减，但不能跳过关键授权和验证。

不必为每次小修改更新所有系统文档。需要同步的普通修改直接 Push 到 `main`，不创建 PR；高风险修改创建 Draft PR；任何模式都不得自动 Merge，也不应把总结学习结果设为每个任务的固定产物。

## 文档重构与内容迁移流程

内容迁移审计不是所有文档修改的必经步骤。

### 触发条件

以下情况必须执行内容迁移审计：

- 删除原有内容
- 重构文件
- 合并或拆分文件
- 调整文件职责
- 跨文件迁移内容
- 大幅压缩原有信息
- 将长期内容改为阶段内容
- 调整权威事实来源

错字修正、格式调整、不改变语义的措辞优化、已确认内容的准确翻译，以及不会造成信息移出的局部补充，通常不需要迁移审计。

### 标准流程

1. 检查被删除、压缩、合并或移出的内容。
2. 将每一项内容分类为永久删除、已在其他权威文件中存在、建议迁移或暂缓处理。
3. AI 先向 Human 提交审计结果和迁移建议。
4. Human 确认前，不得迁移或永久删除重要有效内容。
5. Human 确认后，统一修改来源位置和目标位置。
6. 修改后同时检查来源文件和目标文件。
7. 确认没有遗漏、重复、矛盾或职责冲突。
8. 完整 Review 和验证后才能 Commit。

不得静默删除仍然有效的内容。

### 永久删除

只有内容错误、已经过期、不再具有长期保存价值，或已被权威来源完整覆盖且重复保留会造成冲突时，才可以建议永久删除。

永久删除必须说明理由。

### 已在其他权威文件中存在

必须指出当前权威文件、对应章节或事实，以及是否完整覆盖原意。不得只写“已经存在”而不指出来源。

### 建议迁移

必须指出来源文件、目标文件、原内容摘要、建议迁移后的表达和迁移理由。Human 确认前不得执行。

### 暂缓处理

适用于目标模块尚未设计、文件职责尚未确认、内容归属仍不明确或需要 Human 进一步决策的情况。

目标模块尚未设计时，不得为了迁移一条内容擅自创建新模块。

## Review 与集中修改

- 先形成可以完整理解的 Draft，再进行完整 Review。
- 优先检查事实、职责、边界、结构和信息完整性。
- 措辞和格式润色排在结构正确之后。
- 同一轮发现的问题原则上集中修改。
- 高风险内容可以提前分段验证，但不得制造低价值的小修改循环。
- 精品意味着准确、完整和可维护，不意味着无限打磨。
- 达到 Human 已确认的完成标准后，应停止低价值修改。
- Review 不只检查“写得好不好”，还应检查“是否属于本文件”和“是否遗漏有效内容”。
- Review 发现任务范围扩大时，应先报告，不得直接继续修改。
- Human 应在理解重要结果及其影响后再批准。
- 完成 Review、验证和授权确认后才能 Commit。

## Git 操作与授权边界

| 操作 | 默认边界 |
| --- | --- |
| `git status`、`git diff`、`git log`、`git show` | 与任务相关时可以执行，属于只读检查 |
| 修改文件 | Human 已明确要求修改且范围清楚时执行 |
| `git add` | 普通修改和高风险 PR 均可按本次确认范围执行，不得暂存无关修改 |
| Commit | 完成 Review 和必要检查后，按对应模式执行 |
| Push | 普通修改 Push 到 `main`；高风险修改 Push 到开发分支 |
| 创建 PR | 仅在命中高风险条件时自动创建以 `main` 为目标的 Draft PR；其他情况禁止创建 |
| Merge | 必须由 Human 单独明确决定 |
| Amend | 不得擅自执行，必须单独授权 |
| Reset | 不得擅自执行，必须确认精确目标和数据风险 |
| Rebase | 不得擅自执行，必须单独授权并说明历史影响 |
| 强制 Push | 原则上禁止，仅在 Human 明确理解风险并单独授权时考虑 |

- 当前仓库的普通修改默认采用 Direct Push 模式；如果 Human 只要求本地修改或禁止 Git 写入，则保持本地工作模式。
- Direct Push standing authorization 持续到 Human 明确说“停止直推”或“恢复 PR 模式”。
- 高风险 PR 模式只覆盖创建分支、暂存相关文件、Commit、Push 和创建 Draft PR；Merge 必须由 Human 单独明确决定。
- Handoff 更新不要求单独 Commit，普通维护也不要求每次建立 PR。
- 普通修改完成后可以按 standing authorization 自动 Commit 并 Push 到 `main`，但禁止创建 PR。
- 高风险修改禁止直推 `main`，必须创建 Draft PR。
- AI 不自动 Merge。
- AI 不擅自改写 Git 历史。
- Human 可以在一条明确指令中授权多项操作。
- 多项授权必须包含清楚的操作范围。
- standing authorization 之外的 Git 写操作不得因为“看起来合理”而执行。
- 发现工作区存在未预期修改时，应暂停并报告。
- 除本文记录的 standing authorization 外，允许修改文件不等于同时允许暂存和提交。

## 能力选择原则

- 高复杂度设计、冲突判断和最终审核，应使用足以处理该风险的推理能力。
- 明确、机械、低风险的执行任务，应使用满足要求的最低必要能力。
- 不使用高成本能力处理纯格式化或重复操作。
- 重复且稳定的机械步骤可以自动化，但自动化不得绕过 Human 授权和必要验证。
- 能力选择不得降低准确性、验证强度或安全边界。
- 长期规则不绑定具体模型名称、产品套餐、额度或临时价格。

## 与其他文件的关系

- `Identity.md` 定义 Human 是谁、重视什么，以及希望长期如何行动。
- `Vision.md` 定义长期方向和理想状态。
- `Strategic_Goals.md` 定义当前阶段成果、优先级、成功标准和战略风险。
- `System_Design_Guide.md` 定义系统怎样设计、组织、扩展和维护。
- `Workflow.md` 定义任务怎样被协作、读取、执行、审核、验证和授权。
- `AI_Constitution.md` 定义行为是否允许。
- `Decision_Log.md` 保存重要决定及其理由，但不授权执行。
- `Review/Policy.md` 定义自动审核实现契约，但不作最终决定。
- Handoff 或任务文件记录当前状态、未完成事项和易变上下文。
- 专业模块保存具体学习、项目或领域内容。

本章节只说明职责关系，不复制其他文件的具体内容。

## 更新规则

只有以下内容发生明显变化时，才更新本文：

- 核心协作角色或职责
- 任务分类方式
- 标准工作流程
- 系统文档读取规则或读取时机
- Review 规则
- 内容迁移规则
- Git 授权边界
- 能力选择原则
- Handoff 更新条件

不得因为某次临时任务、短期工具变化或产品界面调整而更新长期 Workflow。

只有相关长期知识实际发生变化时，才更新对应权威文档。
